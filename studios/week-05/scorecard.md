### Where We May Have Been Unfair, and What We Did Not Test (Honesty Clause)

1. **Toy RSA Cryptosystem:** We evaluated signature verification using 64-bit toy RSA with a fixed seed (`seed=7`) and raw textbook verification without standard padding schemes (PKCS#1 v1.5 or RSA-PSS). We did not evaluate resistance to mathematical factorisation or signature malleability attacks on the underlying modulus $N$.
2. **Missing X.509 Extension Checks:** The given `validate` function only checks signature links and the root presence. It does not enforce standard X.509 v3 policy constraints:
   - `basicConstraints` (`cA=True` vs `cA=False`): A compromised leaf certificate could fraudulently act as an intermediate CA.
   - `KeyUsage` / `ExtendedKeyUsage`: Certificates were not restricted by operational role (e.g., server authentication vs. code signing).
   - `NameConstraints`: A subordinate CA could sign certificates for arbitrary top-level domains without restriction.
3. **Revocation Machinery Omitted:** Certificates were assumed to be static. We did not test or benchmark revocation paths (CRLs or OCSP / OCSP Stapling), nor did we evaluate the failure modes of revocation mechanisms (*soft-fail* vs *hard-fail* under active network interference).
4. **Simplified Trust Store Model:** The lab models the trust store as a flat, unprivileged Python `set`. Real operating systems and browsers protect their trust stores via access control lists (ACLs), cryptographic code signing, and hardware-backed keystores, meaning real-world poisoning requires administrative elevation or kernel-level execution.
